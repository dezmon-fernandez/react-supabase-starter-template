# Relational database practices

> Base template — specialize for target stack and project. Replace `[STACK-SPECIFIC]` and `[PROJECT-SPECIFIC]` sections.

Standing rules for schema management, data access, and read-model design in
this repo. The tiebreaker for every choice below, and for future additions:
**readability first** — the store is understood by opening one file, a change
is understood by reading one diff, and no tool or DSL stands between a reader
and the schema. Add a practice here when a decision recurs; each entry carries
its reason in full.

## Schema authority

- `migrations/*.sql` — hand-written, reviewed, forward-only — is the **only
  schema authority**. Nothing generates DDL that applies unreviewed; an
  autogeneration tool may at most *draft* a migration that is then read and
  committed like any other.
- `schema.sql` (repo root, generated by `dbmate dump`) is the **read surface**:
  the current schema as one readable file. To learn the current shape of any
  table, read it — never a migration file. A migration file states history;
  later files may have altered or renamed anything it creates.
- `[PROJECT-SPECIFIC: the typed-mirror module]` is the typed mirror: one typed
  row model per table, changed in the same commit as the migration that changes
  the table.
- Workflow when a migration is added: write the migration → run
  `[PROJECT-SPECIFIC: the schema-regeneration script]` (applies it and
  regenerates `schema.sql` in the exact byte-form the drift gate compares) →
  commit the migration, the refreshed `schema.sql`, and the typed-mirror change
  together. CI fails on snapshot drift, so a forgotten regeneration is a red
  build, not silent staleness.
- Migrations are forward-only: no down migrations, ever. A data-touching
  rollback script against an irreplaceable store is an untested promise;
  recovery is a new roll-forward migration, or a backup restore. dbmate's
  format demands a down block regardless; it stays empty with a comment
  saying so, enforced by `[PROJECT-SPECIFIC: the migration-format test]`.

## dbmate (single apply path)

- **dbmate is the only tool that ever applies a migration or generates
  `schema.sql`** — dev, fresh bootstrap, the test suite, and CI all build
  schema through the same `dbmate up` / `dbmate dump`. There is no second
  apply path to keep in sync, because there is no second path.
- **One database URL**: `.env`'s `DATABASE_URL` is written in dbmate's bare
  `postgresql://` dialect (with `sslmode=disable` — local Postgres has no TLS),
  and `[STACK-SPECIFIC: the config module]` normalizes on load the driver
  suffix its database library needs. One variable serves both tools; bare
  `dbmate up` / `status` / `dump` work with no flags and no second URL to keep
  in sync.
- **`schema.sql` regeneration is one command:
  `[PROJECT-SPECIFIC: the schema-regeneration script]`** — CI's drift job runs
  the same script, so the local workflow and the gate cannot diverge. It
  exists because dbmate's automatic post-`up` dump cannot produce the
  committed byte-form; the three bullets below are the reasons, each encoded
  as one step of the script.
- **Silent-skip guard**: `dbmate up`/`migrate`/`rollback` auto-dump the schema
  afterward by default, but silently skip that dump (green exit, stale
  `schema.sql`) when `pg_dump` isn't on PATH. `.env` therefore sets
  `DBMATE_NO_DUMP_SCHEMA=true` so no `dbmate up` ever auto-dumps; the script
  asserts `pg_dump` exists, then calls the explicit `dbmate dump`, which fails
  loud when it is missing.
- **A pinned postgres client must be on PATH wherever a dump runs** (dev and
  CI). pg_dump ≥ 16.10 embeds a `\restrict` token to mitigate CVE-2025-8714;
  dbmate passes a fixed `--restrict-key` for it automatically (v2.29.4+), so
  this is no longer a flag to manage by hand — but the client's own version
  still has to be new enough to carry the fix, and old/new clients emit
  different output for the same schema.
- **Every dump strips the `pg_dump` client-packaging banner line** (`-- Dumped
  by pg_dump version …`) before comparing or committing (the script's last
  step) — its text names the client's OS/build (`Homebrew` locally, the Linux
  package in CI), which differs by platform even when the pg_dump *version* is
  pinned identically, so leaving it in would make the drift gate red forever
  between the two.
- **Every dump passes `--no-comments`** as an extra argument (`dbmate dump --
  --no-comments`, since dbmate's own fixed flags don't include it): a
  database's `public` schema carries an owner and a comment that are set once,
  whenever that specific database was first created, and never touched by any
  migration — a long-lived dev database and a freshly bootstrapped one can
  legitimately disagree here for reasons that have nothing to do with schema
  content. Keep the `public` schema's owner and comment at Postgres's own
  defaults (`pg_database_owner` / `'standard public schema'`) on every
  database that ever gets dumped, so this never needs revisiting.
- **Adopting dbmate on an already-migrated database has no upstream baseline
  command**: seed `schema_migrations` by hand (`CREATE TABLE IF NOT EXISTS
  public.schema_migrations (version varchar PRIMARY KEY)` then one `INSERT`
  per migration's leading-digit version) so `dbmate up` sees everything as
  already applied instead of re-running it. Probe the exact seed on a
  disposable database first — there is no undo if the versions are wrong.
- Pin the postgres image to a **minor** version (`postgres:16.x`) in
  docker-compose and CI. A minor bump can reshape dump output; an image-tag
  drift then reads as schema drift.
- A snapshot failure is a **hard failure**: `dbmate dump` exits non-zero and
  writes nothing on a failed or missing `pg_dump`. A partial or stale snapshot
  committed silently is worse than no snapshot.

## Destructive-DDL gate

- squawk lints `migrations/*.sql` in CI (`.squawk.toml` pins `pg_version`).
  The load-bearing rules are the data-destruction bans — `ban-drop-table`,
  `ban-drop-column`, `ban-drop-not-null`, `changing-column-type`,
  `renaming-column`, `renaming-table` — because they guard data that cannot be
  recreated once the store accrues history no source can re-serve. A migration
  that predates the gate and already shipped a rename carries its own
  `squawk-ignore-file` comment rather than weakening the rule for every
  migration written after it.
- `.squawk.toml`'s `excluded_rules` are reserved for rules categorically
  inapplicable to this store, each carrying its reason as a comment in the
  file itself. `[PROJECT-SPECIFIC: the excluded rules and their reasons — e.g.
  zero-downtime lock-hazard rules are moot on a small single-writer store;
  re-runnability rules are moot because dbmate transaction-wraps every
  migration and tracks applied versions.]`
- **The gate makes destruction deliberate — it never forbids it.** A genuinely
  needed destructive change overrides the linter explicitly: an inline
  `-- squawk-ignore <rule>` comment on the statement, with the migration's
  header stating the reasoning in full. That keeps destruction a written
  decision without ever weakening the rule for later migrations — a
  config-level exclusion is never for waving one migration through.
- **Dead schema is removed, not retained.** A column or table that nothing
  reads, nothing writes, and that holds no data is not a safety net — it is a
  standing trap: its name promises data it does not hold, and the next reader
  who trusts that promise ships a bug. Before such a drop, verify the element
  is dead and say so in the migration header: all-NULL (or unreferenced) in
  the live store, and no code path reads or writes it. With that shown,
  dropping is the data-integrity move and keeping the column is the hack —
  caution that preserves a lie is not caution.

## Types and constraints

- Money, prices, and probabilities are `NUMERIC` — never float. Floating-point
  rounding compounds across chained derivations; fixed-point is exact.
- Timestamps are `TIMESTAMPTZ`, UTC in the store, converted at the edge.
  Variable text is `TEXT` (`CHAR(n)` pads; `VARCHAR(n)` adds a limit nobody
  maintains).
- A categorical column is always constrained — via a `CHECK` list (few, stable
  values: a `status` column) or a reference-table FK (values that grow or
  carry attributes: a category table). Prefer these over native `ENUM`: adding
  an enum value is DDL with awkward ordering/removal semantics, while a CHECK
  rewrite or a reference-table INSERT is an ordinary reviewed change. The
  application layer validating the same values is not a substitute — the
  constraint is what stops a bad writer that bypasses the app.

## Indexes

- Every index is a paid position: it costs storage and taxes every
  INSERT/UPDATE. Add one for a demonstrated access pattern, not on principle.
- Judge candidates by selectivity (distinct values ÷ rows): near 1, an index
  pays; near 0 (a handful of values over thousands of rows, like a status
  column), a scan wins and the index is pure write-tax.
- Postgres does NOT auto-index FK columns. That is often fine: composite
  natural-key unique constraints already cover the hot leading-column lookups,
  and the classic FK-index failure (parent DELETEs scanning children) cannot
  occur where parents are never deleted. Audit coverage when query patterns
  change:

  ```sql
  SELECT conrelid::regclass AS table_name, a.attname AS fk_column
  FROM pg_constraint c
  JOIN unnest(c.conkey) AS colnum ON true
  JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = colnum
  WHERE c.contype = 'f'
    AND NOT EXISTS (SELECT 1 FROM pg_index i
                    WHERE i.indrelid = c.conrelid
                      AND (i.indkey::int2[])[0] = colnum)
  ORDER BY 1, 2;
  ```

  An FK appearing here is a decision point, not automatically a defect — check
  selectivity and the access pattern before adding anything.

## Data access

- Raw parameterized SQL + typed row models at every boundary. No ORM owns or
  generates the schema.
- The two questions that decide whether any schema-management tool is
  acceptable: **who owns the schema** (must be: the reviewed migrations, not
  model classes), and **is generated DDL reviewed before it touches data that
  cannot be recreated** (must be: yes). A tool passing both is usable as a
  convenience; a tool failing either is rejected regardless of its developer experience.
- The known cost of raw SQL: SQL strings are invisible to the type checker —
  a renamed column fails at test time, not type-check time. The two
  compensating controls are therefore mandatory, not optional: row models
  validate every row in and out, and the integration suite runs against a real
  test database on every change.

## Boundary shapes (the mapping-tax rule)

- **One declaration per shape.** A second type at a boundary is justified only
  where the data genuinely changes shape: vendor payload → parsed value → row
  model (parsing is real work); joined query result → HTTP response schema (a
  published contract is a different thing than a table). Between two shapes
  that are field-for-field identical, there is no boundary — use the one type.
- Litmus: if a mapping function assigns every field across unchanged
  (`out.foo = in.foo`), delete the mapping and the extra type. An identity
  mapper is pure cost: every property added must be re-declared and re-mapped,
  and a missed mapper drops the field silently (`null` in the response, no
  error anywhere). The thin chain fails loud instead — the type checker and
  row validation name the exact spot a property wasn't wired through.
- The cost model for adding a property: edits where the property does real
  work (migration, row model, query, response schema, consumer) are
  irreducible; edits where it is merely re-declared or passed through must be
  zero.

## Adapters

- Place an adapter where the far side is **outside this repo's control**:
  vendor API clients (payload shapes change on the vendor's schedule),
  external-identifier resolution (outside names drift on their own schedule
  and are absorbed by mapping rows, never by guessing).
- Never place an adapter between this code and its own schema. The store is
  the product; domain shape and storage shape co-evolve by definition, so an
  indirection layer between them pays vertical-change tax on every property
  forever to insure against a storage swap the project has committed to never
  making.

## Read models (queries vs views)

- A screen or report gets **one query, shaped for the consumer, in the
  consuming slice's query module** — returning rows the consumer renders
  without transforming. A client-side `.filter().map()` chain reconstructing
  relationships between two fetched arrays is a JOIN written in the wrong
  language in the wrong place.
- Promote a query to a database VIEW only when both hold: the join has
  stabilized (no longer changing with UI iteration), and it has **multiple
  consumers** (an endpoint plus ad-hoc analysis, or a second API surface). A
  view serving one consumer is slice logic living in the shared schema layer,
  where every slice can silently couple to it; and each view change is a
  migration, which is the wrong cost for iteration-speed work.
- Derived data (rates, aggregates, coverage) is computed on read — from
  queries or views — never stored alongside captured facts.

## Modeling rules that a foreign key cannot enforce

A schema can be fully constrained and still encode a false claim about the
world. Each rule below carries the check that catches its failure, because the
database cannot.

- **A vocabulary table holds peers, never a parent and its children.** A
  reference table containing both a category and the members inside it makes
  every membership check pass while the join it exists to protect silently
  fails — the foreign key confirms the value is *in the set*, not that it means
  the same thing as the value it joins to. Before adding a key, ask whether any
  existing key would *contain* it. If so, it belongs in a different table.
- **One concept, one spelling.** When an external source's name and the store's
  name for the same concept both live in the vocabulary, callers split across
  them and neither side is complete. Translate the source's vocabulary to the
  store's at the client boundary, and let the reference table hold exactly one
  key per concept.
- **A uniqueness key is a business rule — write it as a sentence in the migration
  header and read it aloud.** `UNIQUE (account_id, currency)` asserts "an
  account holds at most one balance per currency." Stated plainly, a false
  assertion is obvious; stated as column names, it ships and then silently
  rejects valid rows forever.
- **For every pair of tables that must join, write the join as a test and assert
  it returns rows.** Two tables can each be individually correct, fully
  constrained, and populated, and still never meet. Only executing the join
  proves the vocabularies line up. Any join the product depends on needs a test
  that exercises it end to end.

## What earns a table at all

Before choosing a grain, decide whether the fact belongs in the store. Two questions, in
order.

**1. Does the HISTORY of this fact let you form or test a hypothesis?** If the only use is
"what is it right now," it is a display fact. It belongs in a pass-through read that fronts
the source and never touches the store. The test is whether a hypothesis conditions on it:
"how do delivery times shift in bad weather" cannot be answered without the weather recorded
per past delivery beside its duration, so weather is stored. "Which driver is on shift right
now" is read, acted on, and finished with, so it is not.

Beware the proxy. A fact whose predictive content is already carried by a stored column
earns nothing by being stored beside it. A user's plan tier predicts their request volume,
and the request count is already a column — storing both is storing a measure next to the
thing it measures. The exception is timing: a proxy known BEFORE the event is admissible to
a forecast where the outcome it proxies is not, because a forecast never sees the result at
prediction time. State that timing argument explicitly when it is the reason, or the table
has no reason.

**2. Is that history freely re-collectable later?** This decides WHEN to collect, never
whether. A fact that expires must be captured as it happens or it is gone: a quote or live
status the source overwrites in place is this, which is why such collection runs on a clock.
A fact a primary source retains permanently can be deferred until a hypothesis actually
needs it, at the cost of one backfill — deferring it is free, and so is changing your mind.

Verify retention rather than assuming it. Both directions are common in a single vendor:
one endpoint retains finished records indefinitely, while another bills for history and
bounds how far back it serves.

**Size is rarely the deciding argument.** Profile before invoking it:

```sql
SELECT relname, n_live_tup,
       pg_size_pretty(pg_total_relation_size(relid)) AS total,
       pg_size_pretty(pg_indexes_size(relid))        AS indexes
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 10;
```

An entity-per-row table is thousands of rows and megabytes. One high-frequency time series
dwarfs every other table combined, and its unique index alone can outweigh them. Reach for
the size argument only against a candidate in that second class; for anything else, decide
on utility and let the megabytes fall where they fall.

The real cost of a needless table is not disk. It is the reader who finds a column, trusts
what its name promises, and ships a bug — the same failure the dead-schema rule above
guards against, arriving through addition instead of retention.

## Grain

- **Store the finest grain the ingestion job receives; derive every coarser
  view on read.** A stored summary whose source rows were discarded cannot be
  verified, cannot be re-derived under a corrected definition, and cannot be
  reconciled against a second summary of the same discarded source.
- **Never keep two stored summaries of one discarded source.** They will
  disagree eventually — one job re-runs, the other does not — and nothing
  remains to arbitrate. Either keep the source, or keep exactly one summary.
- **When the source is re-fetchable, prefer its raw form.** Storage is cheap
  next to a re-collection, and a grain chosen for today's question forecloses
  tomorrow's.

## Operations — scale thresholds

Rules that change with size, stated with the size that changes them:

- `postgresql.conf` defaults are correct while the store is small (largest
  table tens of thousands of rows). Tune (`shared_buffers` toward 25-40% of
  RAM, `effective_cache_size`, `work_mem`) at server deployment, against
  observed load — never preemptively on a laptop.
- `pg_dump` backups are the right format while a full restore takes minutes.
  Binary/columnar backup formats earn consideration only when restore time is
  measured in hours — re-evaluate if the store's size makes that true, not
  before.
- Database-level monitoring (query latency, locks, I/O) lands with server
  deployment; until then `[PROJECT-SPECIFIC: the liveness surface — e.g. a
  job-run heartbeat table]` and the test suite are the liveness and
  correctness surfaces.

## Buy before build

Before writing any infrastructure code (a runner, a generator, a retry layer, a
scheduler — anything that is not this project's domain logic), name the
established tool that solves it and reject it **in writing** — in the plan or
the module docstring, with the specific reason (a requirement it fails, a
dependency cost, an authority rule it violates). Domain logic is exempt: no
established tool ships this project's own features. The litmus: if the
rejection reason is only "it's easy to write ourselves," adopt the tool —
hand-rolled infrastructure is easy to write and expensive to keep correct (the
maintained tool absorbed the pg_dump 16.10 landmine upstream; a hand-rolled
version would have eaten it here).

## Verification over indirection

Thin data access is purchased, continuously, by the gate: lint, format check,
import-boundary check, typecheck, and tests — fast, deterministic, run on
every change, with integration tests against a real database.

in defensive layers; if the gate ever becomes slow, flaky, or optional, the
